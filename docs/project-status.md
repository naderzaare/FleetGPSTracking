# وضعیت پروژه و راهنمای ادامهٔ کار

آخرین به‌روزرسانی: ۲۰۲۶-۱۰-۲۴، منطقهٔ زمانی Asia/Tehran

این فایل نقطهٔ شروع ادامهٔ پروژه روی لپ‌تاپ یا کامپیوتر است. ابتدای هر جلسه خوانده شود و پایان کار با وضعیت واقعی، تصمیم‌ها و قدم بعدی به‌روز شود. تصمیم‌های طراحی به معنی پیاده‌سازی یا استقرار نیستند.

## هدف و قدم بعدی

مسیر هدف: دستگاه GPS ← گیرنده ← بافر ماندگار ← RabbitMQ ← سرویس ذخیره‌سازی ← SQL Server.

**قدم بعدی مورد توافق:** راه‌اندازی/استفاده از گیرندهٔ فعلی برای جمع‌آوری نمونهٔ واقعی از دستگاه Teltonika FMB920، سپس تحلیل داده‌ها و طراحی قالب استاندارد رکورد و جدول‌های SQL. توسعهٔ مسیر RabbitMQ و SQL فعلاً در مرحلهٔ برنامه‌ریزی است؛ شروع پیاده‌سازی نیازمند درخواست بعدی کاربر است.

## وضعیت فعلی و شواهد

- گیرندهٔ مستقل تلتونیکا، ثبت capture، شبیه‌ساز پایتون و تنظیمات مانیتورینگ Prometheus/Grafana در مخزن وجود دارند.
- طبق گزارش کاربر در گفت‌وگوی «طرح بافر دیسکی RabbitMQ»، گیرنده منتشر شده و برای حدود ۵۰۰ دستگاه ظاهراً پایدار کار کرده است. این گزارش، تأیید مستقل ظرفیت تولید یا آزمون دستگاه‌های واقعی نیست؛ جزئیات محیط و مدت آزمون باید ثبت شود.
- شاخهٔ فعال هنگام تهیهٔ این یادداشت: `codex/gps-receiver`، با upstream برابر `origin/codex/gps-receiver`.
- آخرین commit محلی مشاهده‌شده: `c8efb97` با عنوان `Add receiver monitoring deployment and Persian guide`. تازگی وضعیت سرور Git در این جلسه با fetch بررسی نشده است.
- تغییرات ثبت‌نشده در گیرنده، متریک‌ها، Compose، داشبورد Grafana و شبیه‌ساز وجود دارد؛ پیش از انتقال دستگاه باید بررسی و منتقل شوند.
- تغییرات مشاهده‌شدهٔ گیرنده شامل جداکردن اجرای سشن از حلقهٔ پذیرش اتصال، ثبت زمان handshake و تجمیع flush با حفظ ثبت پایدار packet پیش از ACK است. صحت این تغییرات در این جلسه دوباره آزموده نشده است.
- تغییرات شبیه‌ساز شامل شروع تدریجی دستگاه‌ها، حالت بدون اتصال مجدد و شمارنده‌ها/تشخیص مرحلهٔ خطاست؛ راهنمای آن در `tools/GpsSimulator/README-fa.md` موجود است.
- نتایج آزمون‌های قدیمی گیرنده در `docs/gps-receiver-validation.md` و قرارداد متریک‌ها در `docs/gps-receiver-metrics.md` آمده است. پروژهٔ تست .NET بنا به درخواست قبلی کاربر حذف شده؛ نتایج تاریخی را نباید آزمون جاری تلقی کرد.
- در این جلسه فقط این سند تهیه شده؛ تست، استقرار، commit یا push انجام نشده است.

## جمع‌بندی معماری مورد بحث

1. هر نوع پروتکل GPS می‌تواند گیرنده و پورت اختصاصی داشته باشد؛ همهٔ گیرنده‌ها رکورد استاندارد مشترک و نسخه‌دار تولید کنند.
2. واحد پیام در جمع‌بندی آخر: **هر پیام یک رکورد**. نام، نوع، واحد و فیلدهای اجباری پس از تحلیل نمونهٔ واقعی نهایی شوند.
3. گیرنده داده را اعتبارسنجی و استاندارد کند، در بافر دیسکی پایدار ثبت کند و سپس تأیید کاربردی به دستگاه بدهد.
4. ارسال‌کنندهٔ پس‌زمینه با شناسهٔ ثابت پیام، داده را به RabbitMQ بفرستد. حذف از بافر تنها پس از تأیید ناشر و اطمینان از مسیریابی موفق انجام شود.
5. RabbitMQ در کانتینر مستقل، با صف و پیام ماندگار و فضای ذخیره‌سازی پایدار قرار گیرد. نوع صف و نیاز به افزونگی هنوز نهایی نشده‌اند.
6. سرویس ذخیره‌سازی در کانتینر جدا پیام استاندارد را بخواند، اعتبارسنجی و در تراکنش SQL ثبت کند؛ ACK مصرف‌کننده فقط بعد از ثبت موفق صادر شود.
7. تحویل مجدد ممکن است؛ شناسهٔ ثابت و قید یکتا/روش مناسب تشخیص تکرار مانع ثبت دوباره در SQL شود. قاعدهٔ تشخیص ارسال مجدد دستگاه نیز باید مشخص شود.
8. مانیتورینگ مسیر کامل شامل رکوردهای ذخیره‌شده، تأییدهای ارسال، حجم و سن دادهٔ بافر، retry، خطا، عمق صف و وضعیت منابع باشد.

ارسال مستقیم به RabbitMQ قبلاً به‌عنوان گزینه بررسی شد؛ جمع‌بندی بعدی برای ادامهٔ دریافت هنگام قطعی RabbitMQ، استفاده از بافر ماندگار محلی بود. بافر فقط از دادهٔ دریافت‌شده و پایدارشده محافظت می‌کند؛ یک دیسک/میزبان به‌تنهایی تحمل خرابی کامل سرور ایجاد نمی‌کند.

در گفت‌وگوی قبلی، پیاده‌سازی بافر در فضای جداگانه شروع و پس از تصریح «فقط پلن، بدون کدنویسی» متوقف شد. طبق گزارش همان گفت‌وگو، تغییرات به پروژهٔ اصلی ادغام یا مستقر نشده‌اند. وضعیت و محل فعلی آن تغییرات در این جلسه بررسی نشده؛ نباید آن‌ها را قابلیت موجود این شاخه فرض کرد.

## مسیر مرحله‌ای تا SQL Server

1. جمع‌آوری capture واقعی از حرکت، توقف، روشن/خاموش شدن خودرو، قطع ارتباط و ارسال اطلاعات عقب‌افتاده؛ ثبت مدل، firmware و تنظیمات دستگاه و مدیریت فضای capture.
2. تحلیل زمان دستگاه/سرور، مختصات، سرعت، اعتبار موقعیت، سوئیچ و IO؛ تفکیک صفر، مقدار ناموجود و موقعیت نامعتبر و بررسی تکرارها.
3. طراحی هم‌زمان قرارداد نسخه‌دار پیام و ساختار SQL، شامل شناسهٔ دستگاه/پیام، زمان‌ها، موقعیت، حسگرها و قواعد تکرار.
4. پس از مجوز پیاده‌سازی: افزودن بافر و ارسال‌کننده، سپس RabbitMQ و مانیتورینگ آن.
5. ساخت مصرف‌کنندهٔ SQL با ثبت تراکنشی، مدیریت تکرار، retry و مسیر بررسی پیام خراب.
6. آزمون قطعی RabbitMQ/SQL، ری‌استارت، پرشدن بافر و تطبیق رکورد از دریافت تا SQL پیش از بهره‌برداری.

## موارد باز پیش از پیاده‌سازی

- ظرفیت بافر و صف، نرخ واقعی رکورد و مدت قطعی قابل‌تحمل؛ تا پیش از وجود مصرف‌کننده، صف رشد می‌کند.
- هنگام پرشدن بافر: دادهٔ پذیرفته‌شده حذف نشود؛ هشدار و رفتار توقف پذیرش/ندادن ACK دقیقاً تعیین شود.
- بررسی عملی ACK کاربردی، timeout و ارسال مجدد در FMB920 با تنظیمات و firmware واقعی.
- سیاست نگهداری capture عیب‌یابی مستقل از پاک‌سازی بافر ارسال باشد.
- جزئیات messageId، ترتیب داده‌های عقب‌افتاده، فیلدهای IO و قاعدهٔ تکرار نهایی شوند.
- دسترسی‌ها، نسخه‌ها، ظرفیت و محل استقرار RabbitMQ و SQL و نیاز به تحمل خرابی میزبان مشخص شوند.

## کار روی لپ‌تاپ و کامپیوتر

- هدف کاربر: ادامهٔ همین پروژه به‌تناوب روی دو دستگاه، با حفظ کد و خلاصهٔ تصمیم‌ها.
- روی هر دستگاه نسخهٔ محلی همان مخزن موجود باشد و Codex روی همان دستگاه اجرا شود. مسیر مشاهده‌شده در این چت `C:\Projects\FleetGPSTracking\FleetGPSTracking` متعلق به لپ‌تاپ متصل از راه دور است؛ وجود این مسیر روی کامپیوتر دوم تأیید نشده است.
- Git سابقهٔ چت‌ها را منتقل نمی‌کند. این فایل و مستندات مخزن مرجع مشترک ادامهٔ کار باشند؛ همگام‌سازی خودکار چت‌ها را نباید فرض کرد.
- شروع جلسه: ابتدا `git status`؛ پس از اطمینان از محفوظ بودن تغییرات محلی، دریافت آخرین وضعیت Git و رفتن به شاخهٔ مورد توافق. روی شاخهٔ تمیز می‌توان `git pull --ff-only` اجرا کرد؛ در صورت خطا، بدون reset یا حذف تغییرات علت بررسی شود.
- پایان جلسه: به‌روزرسانی این فایل، بررسی diff و نبود اسرار/capture واقعی در تغییرات، سپس commit و push تغییرات مورد نظر. commit محلی بدون push روی دستگاه دیگر قابل دریافت نیست.
- تا جای ممکن پیش از رفتن سراغ دستگاه دوم، کار دستگاه اول push شود. کار هم‌زمان روی یک شاخه می‌تواند تعارض ایجاد کند.
- استفاده از نسخهٔ محلی روی دستگاه دوم به روشن‌بودن لپ‌تاپ نیاز ندارد؛ ادامهٔ کار Remote روی لپ‌تاپ نیازمند روشن و در دسترس بودن آن است.
- در این جلسه clone روی کامپیوتر دوم یا انتقال چت انجام نشده است. پیش از جابه‌جایی، تغییرات ثبت‌نشدهٔ فعلی لپ‌تاپ باید محفوظ و منتقل شوند.
